`code` is plain JavaScript. The TypeScript declarations below are documentation only; do not copy type annotations into `code`.
The bundled tools declared below are reachable only through the generated `tools` object inside `code`; they are not separately callable. Other LiteCode tools are outside this SDK and may remain directly callable according to the registry. `libs` contains deterministic pure-JavaScript analysis helpers and exposes no filesystem, network, or process API. Standard JavaScript built-ins are available.
A call resolves to the tool's data. A domain failure rejects `ToolError`. Its `code` is one of `invalid_input`, `not_found`, `invalid_regex`, `stale`, `stale_cursor`, `conflict`, `permission_denied`, `timeout`, `io`, `unsupported`, `internal`. A protocol failure (an extra argument, an illegal value, nesting that is too deep, an integer above 2^53-1, or the in-flight cap) throws `TypeError`. Cancellation, the `run_code` budget, the output cap, and memory or stack limits end the program and cannot be caught.
Permission denial is a catchable `ToolError` whose `code` is `permission_denied`.
`tools.edit` resolves `EditResult{ok,path,message}`. `tools.apply_edits` resolves `{results: EditResult[]}`. Miss, multiple match, missing path, and permission problems set `ok: false` with the reason in `message`; they do not reject `ToolError`. Branch on `ok` or filter `results`.
Use `Promise.allSettled` for a batch. One uncaught rejection ends the program and cancels the other in-flight calls.
LSP errors from edit or write are not in the resolved data. They appear only in this run's outer text.
A read of session lines already in the context window returns empty `lines` with `reason` `"in_context_window"`.
A glob that matches nothing returns `reason` `"no_match"`. A glob whose path is hidden by the default filters returns `reason` `"path_excluded"`.
Pagination dialect: for read, pass `page.next` back as `start_line`; for glob and grep, pass `page.next` back as `cursor`.
The model sees about 64KB of this run. Return a summary, not a raw bulk of data.
Call each binding as `tools["name"](args)`. When `name` is an identifier, `tools.name(args)` is the same function. Each binding takes one argument object. Tool timeouts are internal. The only budget the program sets is `run_code`'s `timeout_ms`.
Return a JSON-serializable value: `undefined` is not JSON, so use `null` or omit the property.

declare const tools: {
  // Apply several independent `{path, old_string, new_string}` replacements in one call inside `run_code`. Pass an object bag with `edits`: a non-empty array. Runs **truly serially** in array order: each successful item is written before the next item runs, so later items on the **same `path` see earlier successful `new_string` values**. Resolves `{ results: EditResult[] }` — `results.length` equals `edits.length`. Each `EditResult` is `ok`, `path`, and `message` (same shape as `tools.edit`).
  //
  // A failed item is **skipped**; later items still run. Even when every item fails, the call still **resolves** with `results` full of `ok: false` — it does **not** reject `ToolError` / `edit_failed`. There is no `replace_all`, no `expected_hash`, no shared multi-block same-file plan, and no aggregate `applied` / `failed` / `blocks` / `details` — count or filter `results` yourself (`results.some(r => !r.ok)`). Empty `new_string` deletes that item's `old_string`. Exact match, unique-hit, CRLF/LF, and BOM rules match `edit`. Path missing, permission denied, miss, or multiple matches for an item → that item's `ok: false` with the reason in `message` only. On success, that item's `message` is a short confirmation such as `applied` (never empty, never structured).
  //
  // If a later `old_string` depends on an earlier change that failed (`ok: false`), that later item will typically miss and resolve `ok: false` with a not-found style `message` — fix the earlier failure or split into another call.   //   ],
  // });
  // if (batch.results.some((r) => !r.ok)) {
  //   return { ok: false, results: batch.results };
  // }
  // // each ok item: message === "applied" (short confirm)

  //   path: "src/c.rs",
  //   content: "pub fn ok() -> bool { true }\n",

There is no `replace_all`, no `expected_hash`, no `edits` array on this tool, and no `blocks` / `applied` / `failed` / `details` / `file.hash` report.

On success, `ok` is true and `message` is a short confirmation such as `replaced` (never empty, never a structured payload).   // return { ok: true, path: edited.path, message: edited.message, exit_code: done.exit_code };
  readonly ["edit"]: (args: EditInput) => Promise<EditData>;
  // Find files by path glob. The result is `base`, `paths`, and `page`. `paths` are sorted by depth, then parent directory, then name. When `base` is `"workspace"`, each path is workspace-relative. When `base` is `"absolute"`, each path is absolute.

  readonly ["grep"]: (args: GrepInput) => Promise<GrepData>;
