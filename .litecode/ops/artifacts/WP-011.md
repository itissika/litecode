## A. code_search / session_search 深挖

### A1. 常关（ISSUE-023）

| 点 | 证据 |
|---|---|
| 默认 | `WorkspaceRetrievalState.desired` 默认 `false`（`src/config/workspace.rs` L41–45） |
| 可见性 | `workspace_readiness_from_engines` 仅 `desired && optional` → Ready；`is_available` 对 workspace optional 要求 Ready |
| Agent 面 | `available_tools` 无 id → `build_tool_list` 不会挂 `CodeSearchTool` |
| 测试 | `retrieval_desired_drives_readiness` 通过；`settings_retrieval_engine_init_and_stop_use_engine_api` 断言 stop 后 catalog 无 code_search；`optional_code_search::workspace_with_code_search` 必须 `enable` + 手工 agent 绑定 |
| 产品张力 | `featured-tools.md` 仍把 code_search 列为特色宽找工具 |

**体验：** 新工作区 agent **默认不能**语义搜代码；须人类 Settings→Engines 打开 retrieval，且 agent 侧还需绑定（测试路径显式插入 binding）。

### A2. 开销

| 组件 | 行为 | 证据 |
|---|---|---|
| Worker 子进程 | `CodeSearchEngine::warmup` → `spawn_ready_worker`（可 CPU-ORT 回退） | `src/engines/code_search_engine.rs` |
| 嵌入 | ORT WOQ 产物 `artifacts/ort-lin-q8-emb-q4-bs128-a1.onnx`；缺则报错；RSS 归因 `worker_os_pid` | `ort_embed.rs`、engine 注释 |
| 磁盘索引 | `.litecode/index/`：`meta.json` / `chunks.jsonl` / `vectors.usearch` / `job.json` | `meta.rs`、`store.rs` |
| path_index | 独立内存 Explorer 目录（reconcile **不**随 retrieval 启动） | `path_index/mod.rs`；`reconcile_does_not_start_the_path_index` |
| Session 稀疏账本 | FTS5 chunk 索引；idle tick / 查询后维护，不挡查询 | `session_search/sparse.rs`；`serve/router.rs` |

开销在 **desired=true 之后**才持续（worker + 索引 + 可选 ORT）。常关时无常驻 worker，但特色工具也不可用——开销与可用性绑在同一开关上。本轮不另开「内存数字」issue（无本机基线测量）；记入报告供后续 WP 量化。

## 推荐方案（冻结讨论用 · 人话）

> 本 WP **不继续改产品形状**。下面只给 Andy/GM 拍板用的选项与倾向；落地另开 WP。

### 1. 默认常关（ISSUE-023）

**问题一句话：** 宣传上是特色搜代码工具，新工作区默认却关着，agent 工具表里根本看不到。

| 选项 | 做法 | 代价 |
|---|---|---|
| **A. 默认打开 retrieval** | 新工作区 `desired=true`（或首次打开工作区时引导一键开） | 冷启动/索引有 CPU·磁盘开销；弱机上要可关 |
| B. 默认仍关，但产品面诚实 | 从「特色默认可用」叙事改成「可选引擎」；设置里更醒目 | 不改默认行为；特色能力继续沉默 |
| C. 默认关 + agent 可见「未启用」壳 | 工具仍出现在表里，调用立刻返回可行动错误（指向 Settings） | 要动工具可见性模型；比纯常关诚实 |

**倾向：A（新工作区默认开），弱机/省电场景保留一键关。** 理由：和 featured-tools 承诺对齐；开销可用「首次后台暖机 + 可关」消化，比「默认看不见」更符合产品名头。若 Andy 更怕默认开销，退而求其次用 **C**，不要停在 B（叙事和实现继续打架）。

### 2. 暖机 / 超时（ISSUE-024）

**问题一句话：** 工具自己空等最多 30 秒，管线超时也是 30 秒，冷启动几乎必然堵死整轮 turn 或踩线超时。

| 选项 | 做法 | 代价 |
|---|---|---|
| **A. 短等 + 明确「还在暖」立刻返回** | 同步等待砍到几秒（如 2–5s）；未 Warm 则返回结构化 waiting（可带进度），**不**占满 timeout | agent 可能多一轮重试；要教模型读 waiting |
| B. 异步暖机：调用只触发 start，立即返回「已开始，稍后再搜」 | 不阻塞 turn | 要会话内重试策略；首搜体验仍是两步 |
| C. 拉长工具 timeout（如 120s）继续傻等 | 实现最省事 | turn 更卡，体感更差，不推荐 |

**倾向：A。** 执行门本意就是「等待或失败」，不是「把 turn 钉在 sleep 上」。暖机应在引擎侧后台推进；工具面给短窗口后诚实返回，timeout 只作真正失控的保险丝，不要和暖机预算同一数字。

### 3. 等待文案（ISSUE-025）

**问题一句话：** 只说 Try again shortly，不说要不要去开 Engines；同仓 webfetch 已经会指路。

| 选项 | 做法 | 代价 |
|---|---|---|
| **A. 按原因分支文案** | `desired=false` →「请到 Settings → Engines 打开 retrieval」；Warming/stale →「引擎启动/刷新中，稍后再试（可看 Engines 状态）」 | 要区分原因码 |
| B. 统一加一句 Settings 链接 | 所有 waiting 末尾都加 Engines 指引 | 略吵，实现简单 |
| C. 只改文档/提示词，不改工具输出 | 只改文档 | agent 运行时仍看不见，不推荐 |

**倾向：A（与 webfetch 同级）。** 文案必须可行动，且区分「没开」和「开了但还没好」，避免用户/agent 空转重试。

### 4. session 静默降级（ISSUE-026）

**问题一句话：** code_search 没 Warm 时 session 搜悄悄只剩词法腿，描述也不说会漏语义命中、故意不刷索引。

| 选项 | 做法 |
|---|---|
| **A. 降级要出声** | 非 Warm 时结果带 warning：`semantic_unavailable` / `index_may_be_stale`；description 写明依赖 retrieval Warm |
| B. 非 Warm 直接失败（与 code 门对齐） | 强迫先开引擎 | 可能过严：词法腿仍有价值 |
| C. 维持静默，只改内部注释 | 不推荐 |

**倾向：A。** 契约允许滞后少召回，但**不许瞒着调用方**。词法腿可继续用；语义腿缺席和「查询前不 refresh」必须在工具描述 + 单次结果表面上可见。与 ISSUE-023/025 联动后，常关时至少不会被当成「全家桶语义检索」。
