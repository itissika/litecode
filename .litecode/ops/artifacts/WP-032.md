## 0. 根因（实地排查）

### 0.1 GM 15 分钟被叫醒 7 次（events/inbox.json + .tmp/wp_watch.log）
08:07–08:22Z（16:07–16:22 HKT）这段时间 wp_watch 投递了 7 次：08:07 四次（WP-021/022/024/027），08:14 两次（WP-021/022），08:19 一次（WP-021）。之后 WP-021 几乎每 5 分钟一次（08:24、08:39、08:44、08:49），08:50 又由 tick 重复发了一次。原因有五条：
1. **ack 之后就会重发**：`scanAndEmitWpTimeouts` 去重时只看「本段计时内有没有**未 ack** 的事件」。GM 一 ack，下一个 5 分钟周期又发一条新的。所以同一个卡点会一直响，直到状态变化为止（WP-021 共 9 条）。
2. **父包被子包连带**：WP-021（gm）和 WP-022（gm 当 owner）处在 in_progress，只是因为子包还在跑。父包 owner 当时没有自己要做的动作，照样被叫醒。父子链没有合并，一条链会发多条。
3. **target 不等于真正收到的人**：WP-024/027 的 target 是 backend_mid，但 wp_watch 只有一个 webhook（GM 回调），所有 wp_timeout 都推给了 GM。inbox 里这两条也是 gm ack 的。
4. **两个发事件的进程**：tick（08:50:29，source=ops.tick）和 wp_watch（08:49:16）各自扫描、各自 emit。前一条刚被 ack，tick 就又发了一条。
5. 计时口径：in_progress 也算卡点（v13 起沿用）。父包在等子包时并不卡，这一条和第 2 点是一回事。

### 0.2 16:11 重启丢事件（emit_event / wp.mjs emit / wp_watch）
- wp_watch 只投递 `team_ops.wp_timeout`。`approval_requested` / `acceptance_requested` 只写进 inbox，从来不推。重启前后 08:08 WP-024 和 08:10 WP-027 的 acceptance_requested 就属于这种：没有推送，只能等 GM 自己 tick 才看得到。
- 重启窗口：08:07:26 的 cycle 之后，下一条日志是 08:14:45（手动 `start`）。没有 supervisor 退出记录，说明是整机断电式重启。08:12 那个周期整体缺失，box 上没有 systemd/cron 能自动拉起 watcher，只能靠 tick 的 watcher_down 提醒，再由人手工 start。08:24→08:39 又缺了两个周期（疑似暂停），原因未查明。
- 写盘不安全：emit_event、ack_event、wp.mjs 的 emit、超时扫描都是对 `events/inbox.json` 做**整文件读-改-写**，用的是普通 `writeFileSync`：
  - 不加锁：几个 bot 并发写时，后写的会把先写的覆盖掉（丢更新）。
  - 写入不是原子的：重启时正好在写，文件会被截断。
- wp_watch 先 POST 再保存 delivered：如果在两步之间崩溃，会重复投递，但不会丢。
- 现在的 inbox 里，每条 submit/deliver 日志都能找到对应事件（对过 39 条，没有重复 id）。所以「丢的那一条」更可能是**没被推送**（上面第一点）或者**重启窗口里没扫到**，而不是写盘丢失。这个判断要 GM 确认丢的是哪一条（见第 7 节问题 2）。

### 0.2b E-1791792744885-WP022：ack 时报 missing event（GM 让查）
- **结论：已经发出去了，但从来没落盘。** 落盘前机器就断了，inbox、日志、状态三处都丢了。
- **时间对得上**：1791792744885 = 08:12:24.885Z（16:12:24 HKT），正好是 worker 985359 上一轮 cycle#17（08:07:24.838）之后 5 分钟的 cycle#18。WP-022 那段计时里的上一条事件（08:07:24.839）已经被 GM ack，按 v14「ack 后重发」的规则，这一轮会生成一条新的 WP-022 超时，id 的时间戳和这个规则完全吻合。
- **GM 收到过**：GM 是拿着这个 id 去 ack 的。这个 id 只可能来自 webhook 回调，因为本地任何地方都没有它。
- **磁盘上全都没有**：
  - 全仓 grep 这个 id，0 处命中（inbox.json、log.jsonl、tool_traces.jsonl、.tmp/wp_watch.log、wp_watch.state.json 都没有）。
  - `git log --all -S` 也没有（期间没有 commit 或 stash）。
  - wp_watch.log 在 08:07:26 的 cycle#17 之后，下一行就是 08:14:45 的手动 start。cycle#18 应该写的 `delivered … http=200` 和 cycle 汇总都不在。
  - delivered 一共 12 条，不含它。
  - tool_traces 和 log.jsonl 在 08:10:44 到 08:14:57 之间是空的。
  - 进程 START 时间显示 17:53，但日志写的是 16:14 启动，pid 1 是 pod-daemon。说明 pod 是从快照或没刷盘的状态恢复的：断电前还在页缓存里、没 fsync 的写入都没了。
- **v14 的写法有两个问题**：
  1. inbox、日志、state 用的都是普通 `writeFileSync`/`appendFileSync`，没有 fsync。
  2. 投递顺序是「扫描时写 inbox → POST → 写 delivered」，POST 成功并不说明前面的写入已经落盘。所以机器一断，就出现了「对方收到了，本地没有」。
- **v15 怎么防**：
  - 所有事件写入都改成加锁、写 tmp、fsync、rename、再 fsync 目录。可投递事件同时 fsync 追加到 `events/outbox.jsonl`。wp_watch **只从 outbox 取待发事件**，所以 POST 发生时这条事件一定已经在磁盘上。测试第 6 组让接收端在收到请求时去读盘，确认 inbox 和 outbox 里都已经有这条事件。
  - delivered/retry、心跳、日志也都 fsync。
  - 万一 POST 之后、写 delivered 之前断电，重启后会再发一次，接收端按 `x-litecode-event-id` 去重。也就是说只会重复，不会丢。
  - ack_event 遇到未知 id，会明确报错并说明原因。

## 1. 实现方案

### 1.1 超时按链合并（_lib.scanAndEmitWpTimeouts、tick、wp_watch）
- **谁该动手**：awaiting_approval 和 review 由 approver 动手；in_progress 由 owner 动手，**但如果它有未封的子包，它自己不算卡点**（在等子包），这时卡点往下找。
- **每条链只发一条**：把所有 stale 的 WP 按根节点分组，每条链只取「离卡点最近的那个需要动手的人」，也就是最深的 stale 节点对应的 actor。同一条链上其他 stale 节点记进 `meta.merged:[ids]`，不单独发。
- **matter 去重**：matter key 定为 `wp + status + status_entered_at + actor`。
  - 同一个 matter 已经 ack 的，在**重提醒间隔**内不再发。间隔默认 60 分钟，至少一个周期，可以用 `--realert-min` 调整（数值待 GM 定）。
  - 没 ack 的 matter 也不重复发。
  - 状态变了，或者 actor 变了，就是新 matter。
  - 升级规则沿用 v13：没 ack 超过 5 分钟就上升一级，每段计时只升一次，顶层止于 gm，没有 andy 级。
- **只有一个发事件的进程**：watcher 健康时 tick 只报告、不 emit，只有 watcher 心跳失效时 tick 才兜底 emit。两边共用 1.2 里的锁和 matter 去重，就算同时跑也不会重复。
- **投递对象**：webhook 只推 actor 是 gm 的事件（含升级到 gm 的）。actor 是其他人的只进 inbox，由对方的 tick 消费。payload 新增 `actor`、`merged`、`matter_key`。（是否这样做见第 7 节问题 1。）
- 老 WP（没有 parent、goal、history）：每个包仍然自成一条链。只加两点：「ack 后重提醒间隔」和「单发事件进程」，event 字段只增不改。这算行为修正，需要 GM 认可（第 7 节问题 3）。

### 1.2 事件先落盘再发（_lib 新增 eventStore；emit_event / ack_event / wp.mjs / scan / wp_watch 改用它）
- `withLock(path)`：用 `fs.openSync(lock,'wx')` 建锁文件，里面写 pid 和 ts。等锁时退避重试，最多等 5 秒。锁的 pid 已经不在、或者超过 30 秒的，算陈旧锁，可以抢。
- `appendEvent / ackEvent`：拿锁 → 读 inbox → 修改 → 写 tmp → fsync → rename，原子替换。**先落盘，再返回或投递。**
- outbox：`events/outbox.jsonl` 只追加，每行 `{event_id, ts, type, target}`，加锁写入并 fsync。投递状态仍然记在 `.tmp/wp_watch.state.json`，也改成原子写。
- wp_watch 每个周期以及**启动时**都先把 outbox 里「没送达、没 ack」的条目排空。投递类型从只有 wp_timeout 扩到 approval_requested 和 acceptance_requested（只投 target 是 gm 的，和 1.1 一致）。重复投递靠 `x-litecode-event-id` 幂等，GM 端按 id 去重。
- 重启后自动恢复：box 上没有 systemd/cron。tick 发现 watcher_down 时，可以加 `--autostart` 直接执行 `wp_watch start`，env 从调用方继承（需不需要待 GM 定）。

### 1.3 Issue 编号加锁（新增 tools/issue_new.mjs = ops.issue_new；validate_all 加 issue 校验）
- `issue_new --as <id> --title T --domain D [--severity ..] [--wp WP-x] [--body-file F]`。
- 先锁 `issues/.lock`，然后取 max(issues/*.json, `git show HEAD:` 里已有的 issue 号, `issues/.reserved` 墓碑) + 1。用 `'wx'` 创建文件（已存在就失败，绝不覆盖），写 history 第一条，最后放锁。打印分配到的 id。
- `issues/.reserved` 记录作废的号：031（覆盖事故）和 006。这些号不会再分配。
- validate_all 新增检查：文件名和内部 `id` 一致、id 不重复。冲突直接报 error。
- 已有的 issue 文件一个都不改。

### 1.4 cargo/rustup 在非登录 shell 下默认可用（系统依赖，GM 批后执行；本步没动）
- 把 `~/.cargo/bin/` 里的 rustup proxy（cargo、rustc、rustup、cargo-clippy、cargo-fmt、rustfmt、rustdoc、clippy-driver 等）换成和 `/usr/local/bin` 一样的 wrapper 脚本，内容是先设置 RUSTUP_HOME/CARGO_HOME 默认值，再 exec ops toolchain。这样不管 PATH 先后顺序如何，都会落到 ops toolchain。原文件备份到 `~/.cargo/bin.bak-<ts>`。
- `~/.rustup`（现在是空目录）改成软链，指向 `/workspace/litecode/.litecode/ops/.toolchain/rustup`。这是兜底：任何没设 RUSTUP_HOME 的 rustup proxy 都能找到 default toolchain。
- 新增 `tools/toolchain_check.mjs`（ops.toolchain_check）：在三种环境下各跑一次 `cargo -V` 和 `rustup show active-toolchain`，并打印 which、PATH 前几段、RUSTUP_HOME 是否设置。三种环境分别是：当前继承的 env、`env -i` 最小 env、`bash -lc`。任何一种失败就退出码 1。tick 可以顺带报告结果（不 emit）。
- 不改 /etc/environment 和 profile.d（它们本来就对）。不碰 E 盘，不碰产品代码。

## 3. 测试计划（临时副本，跑完清理；剥掉 webhook env，用本地 http 假服务器接收投递）
