## 1. 实现方案

### 1.1 看板结构（board.schema.json + validate.mjs）
WP 新增可选字段（老 WP 不填也合法）：
- `parent`：父包 id 或 null。null 表示顶层包。
- `goal`：上级给的目标（字符串）。新建包必填，老包可空。
- `approver`：上级审批人（agent id 或 andy）。缺省时读 `reviewer`，现有 20 个 WP 不需要迁移。
- `content`：负责人填写的内容，形式为 `{ kind: "direct"|"split", text }`；`split` 表示内容就是它的子包。
- `history`：审批记录（append-only），形如 `[{ts, actor, action: submit|approve|reject|reopen|close, note}]`。

状态枚举新增 `drafting`、`awaiting_approval`，原有状态保留。

validate 新增检查：
- `parent` 必须存在且不能指向自己；顺着 parent 往上走不能有环。
- approver 必须是已知 agent 或 andy。
- `done` 的父包，子包必须全部是 done 或 cancelled。父包里如果有 blocked 的子包，`history` 里必须有一条 approver 的 close 记录。
- id 仍然用 `WP-NNN`，不支持带点编号。层级只看 parent，以后要迁移成带点 id 时再加一个 alias 字段。

### 1.2 生命周期命令：新增 `ops.wp`（`tools/wp.mjs`）
所有子命令都复用 wp_gate 的写入方式：写入后跑 validate，不通过就回滚；同时写 log 和 history，刷新看板表，记录 trace。

| 子命令 | 谁能用 | 作用 |
|---|---|---|
| `wp new --parent WP-x --title --goal --owner [--approver]` | 父包负责人 | 建子包，初始状态 drafting，approver 默认是父包负责人。上级不能替下级建包：`--as` 必须等于父包 owner |
| `wp fill --id --content-file/--text [--kind direct|split]` | 负责人 | 填写内容，只能在 drafting 状态下做 |
| `wp submit --id` | 负责人 | drafting 变 awaiting_approval，然后发 `team_ops.approval_requested` 事件给 approver |
| `wp approve --id` | approver | awaiting_approval 变 ready（之后负责人用 gate 推到 in_progress） |
| `wp reject --id --note [--reopen WP-child,...]` | approver | 退回 drafting；可以同时把指定子包从 done/blocked 重开回 drafting |
| `wp close --id --to done|blocked` | approver | 封包。父包要求所有子包都已封完；有 blocked 子包时要写明原因 |
| `wp tree [--id WP-x] [--json]` | 任何人 | 以父包为根展开子包树：状态、负责人、审批人、产物 |
| `wp summary --id WP-x` | 任何人 | 列出一个包下所有子包的状态、产物路径和最近的 history |

身份：用 `--as <agent_id>` 表明自己是谁（和现在的 `--source` 一样，靠自律，不做鉴权）。gm 和 andy 的特权只在上表列出的场景里生效。

### 1.3 门禁（改 wp_gate，不改变旧行为）
- 声明了 `goal` 或 `parent` 的包是新模型包。新模型包进入 `in_progress` 前，history 里必须有 approve 记录，否则拒绝。
- 新模型包推到 `review` 或 `done` 时，子包必须全部封完。推到 `done` 只能由 approver 来做（检查 `--source`）。
- 老 WP（既没有 parent 也没有 goal）保持旧行为。`--dry-run` 和 `--kb-nodes` 保留。

### 1.4 超时与升级（改 _lib 的超时扫描 + wp_watch）
- 原有的超时判断（in_progress/review 状态连续超过 1 小时，工作时段内）扩展到 `awaiting_approval`。
- 第一次超时，事件的 target 是该包的 approver。如果事件下一个周期（5 分钟）还没被 ack，就再发一条 `escalated: true` 的事件，target 是 approver 的上级，也就是父包的 approver；**顶层包只升到 gm 为止**（GM 决定 4：升级链里没有 andy 级；approver=andy 的包升级目标按 gm 计；要不要告诉 Andy 由 GM 判断）。老 WP 不升级。
- webhook 消息体增加 `level`（深度）、`parent`、`path`（从根到本包的链）、`target`、`escalated`。原有字段不变。

### 1.5 看板展示
- board.md 的「WP 状态」表改成按父包缩进展开的树。老 WP 全部当顶层显示，不会出现空列。
- tick 输出增加 `awaiting_approval_wp`。

## 3. 测试计划（`wp.test.mjs`，在临时副本里跑）
1. schema：老 board 原样通过；parent 不存在、自环、两节点成环三种情况都会失败。
2. 权限：非父包 owner 建子包会被拒；非 approver 执行 approve、close 或推 done 会被拒。
3. 状态机：drafting → awaiting_approval → ready → in_progress → review → done 走通；没有 approve 直接进 in_progress 会被拒。
4. 父包封包：有子包没封时 submit、review、close 都会被拒；有 blocked 子包时 close 必须带 note。
5. 退回：reject 后回到 drafting；`--reopen` 能把指定子包从 done 重开回 drafting，并写入 history。
6. 超时：awaiting_approval 超过 1 小时，先发给 approver；下一个周期没 ack，升级到上一级；webhook 带上 level、path 和 escalated。
7. 兼容：现有 20 个 WP 跑 validate_all、tick、wp_gate 的结果和以前一致；wp_watch 的旧字段不变。
8. 失败回滚：故意让 validate 失败，确认 board.json 没被改动。
