# WP-193 审阅 brief — PTC / code 模式（agent 面）

**分支：** `feat/tool-contract-ptc`（实验分支；本地已切）  
**口径（Andy）：** 架构优先 + run_code 管线 + 若干 tool 设计问题；**关注 agent 是否易理解、易用**；少陷工程细节与人类侧 UX。  
**产物：** 一份**总分结构、易于阅读**的审阅报告 md（细节放附录留档）。GM 审读确认可读后，**通过聊天发给 Andy**，再封包。

## 范围（做）
1. **架构**：PTC/code 模式在 agent 工作流里的位置与边界是否清晰（相对 direct/普通工具调用）。
2. **run_code 管线**：从「模型决定写代码 → 执行 → 拿回结果/错误」整条链路对 agent 是否可预测、可纠错（契约、失败形态、预算/超时语义等，写到「agent 怎么理解」为止）。
3. **若干 tool 设计**：尤其进入 code 模式的文件类工具（read/edit/write 等）与 run_code 的配合；说明文案、成功/失败契约是否让模型少猜。
4. **agent 体验轴**：易理解 / 易用 / 易排错 / 是否鼓励错误用法；对照 docs/ptc 章程与现行实现。

## 非范围（不做或轻触）
- 人类侧卡片/设置 UI 体验深挖（web 视图已删 run_code 专用展示，仅作事实备注）。
- 纯工程债清单（性能、实现细节）除非直接损害 agent 可理解性。
- 不要求改码；本包是审阅，结论可建议后续包。

## 报告形态（硬性）
- **前半：总分结构** — 总评（一句话 + 分数或档位）→ 若干大结论（每条一段可读散文，不是 bullet 海）。
- **后半：附录** — 证据、文件路径、问题明细留档。
- 路径：`.litecode/ops/artifacts/WP-193/review.md`
- Andy 最终要的是「能一口气读完的报告」，不是密密麻麻问题清单。

## 验收
1. review.md 符合上述形态，GM 认为易于阅读。
2. GM 已把报告正文（或精华）通过聊天发给 Andy。
3. 可封包 close done。
