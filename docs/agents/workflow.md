# 工作流

骨架，不是纪律。哪条被实际验证有效，再把它写成硬规矩。

## 新功能 / 新行为

1. 一句话说清「改完能做什么」。说不清就先问，别动手。
2. 定验收：什么现象算成了。能写成命令或可观察行为就写。
3. 只改最小的一块，跑验收。
4. 没过先诊断，别盲改。
5. 过了再问一句：要不要补一条测试证明它。

## 修 bug

1. 先复现。复现不出来，不改。
2. 先指出原因（读到哪一行、什么条件触发），再动手。
3. 改完重跑原复现路径，原症状消失才算修好。
4. 顺手看见的别顺手改。

## 只问不改

回答问题就行，不动工作区。

## 收敛

同一套检查连跑两次都绿才算收敛。红了当场处理，不许重跑碰运气。

## 经验

踩坑当场记一行，不等收尾总结。进库前过四道门：

1. **能写成动作**：「下次遇到 X，先做 Y」。写不成动作的，不是经验。
2. **有代价**：哪次、什么现象、白花了多少时间。没有实例的是空话。
3. **可验证**：做 Y 能看出对错。看不出的是个人偏好，不进。
4. **有归属**：落进对应域的节点（session / tool / context …），跨域才单列。

写的时候连失效条件一起写：一旦它不再适用就删，不留档。
