# Code 模式（PTC）执行章程

> 本文件是 code 模式这条工作线的**唯一权威**。来源：产品负责人的直接决策 + 知识库中 `status : enabled` 的节点 + `AGENTS.md`。
> 不是权威：`dev/archive/` 下的旧文档、`status : pending` 的知识节点（只当作代码现状描述，不当作决策）、`dev/参考/` 下的第三方代码（只当作参考，不当作决策）。
> 冲突时以本文件为准；本文件只由编排者根据产品负责人的决策修改。

## 1. 产品目标

把 code 编排工具调用（模型写一段程序，通过生成的 `tools.*` SDK 编排调用工具，只把最终结果交回上下文）做成 tool 管线的一等公民，脱离原型，达到最小完整产品闭环。这是跟进业界已有共识的基础设施，不是造新特性。

产品体验：

- 人类用户在前端几乎感觉不到变化。
- 设置里 agent 的 tool 绑定页面，被声明为 code 模式的工具卡片上多一个「code mode」标识。是否走 code 不是用户能选的：工具启用了，它就是 code 模式。启用方式不变。
- 权限体系不变：不做 per-agent 的权限预设；agent 怎么设计由用户负责。
- 消息列表中的工具调用视图保持 raw 格式，不做特殊设计。前端视觉只做最小改动，由产品负责人视觉确认。

## 2. 已定决策

**D1 per-tool 声明式互斥。** 每个工具声明自己的调用面：`Direct`（默认）或 `Code`。声明在工具定义处，不在中心名单里。声明为 `Code` 的工具不出现在 direct 工具列表中，也不允许 direct 调用。direct 与 code 长期共存，mixed 是常态。

**D2 首期 code 工具集只含核心文件工具。** `read`、`glob`、`grep`、`edit`、`write`。写工具 code 化是首期必须落地的范围。其余工具保持 Direct：bash 系列、subagent、todo/plan、knowledge、litecode_workspace、session_search、code_search、lsp、webfetch、websearch、ask_user、custom、mcp。

**D3 custom tool 首期保持 Direct，但架构必须朝支持它演进。** 投影、准入、SDK 生成、执行路径不得按工具来源（内置/custom）分支；一个非内置的测试用工具声明 `Code` 时，必须与内置工具走完全相同的路径。

**D4 MCP 不进入 code 模式。** MCP 工具恒为 Direct，不为它做 SDK 适配。MCP 功能本身保留不变。

**D5 Runtime：嵌入式轻量 JS 引擎，无 ambient 能力。** 默认选型 QuickJS（通过 `rquickjs`，优先 QuickJS-NG 后端）在进程内执行，每次 `run_code` 一个全新的 runtime/context，不保留跨调用状态。程序语言是 JavaScript（ES2023，async 函数体，支持顶层 `await` 与 `return`），不支持 TypeScript 语法。程序没有文件、网络、进程、计时器等任何 ambient 能力，唯一出口是宿主注入的绑定（`tools`）与纯计算辅助（`libs`）。若 `rquickjs` 在 Windows MSVC 上无法稳定构建或无法满足中断/内存上限要求，退回纯 Rust 引擎（如 Boa），由 runtime 阶段的验证结论决定。Node 子进程方案整体移除。
已接受的残留风险：引擎在进程内，若引擎本身有内存安全缺陷，影响宿主进程。runtime 边界（§3 I6）保证以后可以把执行移到子进程而不动上层。

**D6 网络：不提供。** code 模式中没有任何网络能力；webfetch/websearch 保持 Direct。

**D7 审批：与 direct 同一条权限管线，审批等待不计入程序预算。** 嵌套调用触发 Ask 时，经同一个 PermissionSink 弹出同一种卡片；等待期间暂停程序预算时钟；拒绝时该嵌套调用得到类型化的拒绝结果，程序可继续；等待期间用户取消，按 I7 封口。

**D8 嵌套调用账本进入外层结果内容。** 外层 `run_code` 的 `function_call_output` 内容由三部分组成：按提交顺序的嵌套调用摘要（每条一行：序号、工具名、关键参数摘要、终态，不含结果正文，数量有上限）、程序日志、最终返回值。transcript、session search、compact、resume、UI 都只读这一个 Item，不另建第二份记录；审计日志只是派生物。

**D9 `run_code` 是传输，不是用户可见的工具开关。** 当某个 agent 至少启用了一个 Code 工具时，`run_code` 自动出现在该 agent 的工具列表中；否则不出现。它不出现在设置的工具开关中。它本身不携带任何权限，在权限目录中显式登记为放行。

**D10 投影适用于所有调用方。** 主会话与任意深度的子代理，都在各自可见性过滤之后做同一次投影。没有环境变量开关，没有 depth 特判（运行时替换完成之前允许保留一个临时总闸，关闭时所有工具视为 Direct）。

## 3. 架构不变量（每个阶段的验收都要对照）

- **I1** 每个工具恰有一个调用面，来自工具自身的声明。
- **I2** 可见性与执行双重保证：投影时不出现在错误的一面；执行器在权限策略求值之前，按调用方（Direct / Code）拒绝错误的调用，并返回路由提示（如 `` `read` is only available as tools.read inside run_code ``）。
- **I3** 每个调用方的 direct 列表、SDK、绑定白名单由同一次投影、从该调用方自己的可见工具集派生。
- **I4** Code 工具的准入门：输入 schema 完整、输出（data）schema 非空、可确定性渲染为 SDK、名字无碰撞；运行时按输出 schema 校验返回值。不合格的工具从两面都移除并产生可见诊断，绝不出现「direct 已摘、SDK 失败、`run_code` 照常运行」。内置工具的准入由测试强制。
- **I5** 嵌套调用与 direct 调用进入**同一条**管线：输入校验、授权、敏感路径 floor、审批、写锁、执行后的全部副作用（文件提醒、计划修订检测、LSP 反馈、检查点等，凡 direct 有的）、审计、取消、结果终结化。不存在第二条执行路径。
- **I6** runtime 对工具与会话无感：输入是程序、命名绑定、预算、取消、限额；输出是日志、值、正交的失败种类、调用日志。换引擎或移到子进程不需要改工具侧。
- **I7** 取消是封口：任何终止路径（完成、取消、超时、异常、限额）都先向所有在途嵌套调用发出取消，在宽限期内等待它们结束并记录各自终态，然后才结束程序；外层一定写出 `function_call_output`，账本中不丢条目；外层超时不覆盖已完成的内层结果。
- **I8** 权限只收紧：`run_code` 不提供任何额外权限；程序可达的能力不超过绑定集合。
- **I9** 内核只有一套 Item 真相；不新增 Message/Stream 类型，不新增 Item 种类。
- **I10** 结果诚实：失败种类正交（语法错误、异常、超时、取消、限额、非法输出、内部错误）；跨边界的值必须可无损表示为 JSON（`NaN`、`Infinity`、`undefined` 值、`BigInt`、循环引用一律判非法输出）；runtime 的输出上限是唯一硬顶，外层只做常规落盘呈现，不再二次截断。
- **I11** `run_code` 的描述（含 SDK）是该调用方 code 面的纯函数，不含权限、depth、cwd 等易变量，保证请求前缀稳定。

## 4. 范围

做：上面的一切；系统提示中与工具集无关的工具使用指导（被删掉的部分）需要恢复，并补上简短的 code 模式指导；旧会话中 direct 的 read/edit 等工具卡片仍能正常回放。

不做：MCP 的 code 化；custom tool 首期 code 化；持久 REPL；网络；TypeScript 语法；任意 `import`/`require`；per-agent 的 code 开关或权限预设；消息列表中 `run_code` 的专门视图；bash/subagent 的 code 化（未来目标，但不在本轮）。

## 5. 阶段与门禁

每个阶段：实现 → 独立对抗审查 → 修复 → 门禁全过 → 提交（只提交到本地分支，不推送）。

通用门禁：`cargo check` 通过；本阶段新增/修改的测试与既有相关测试通过；改了 `web/` 时 `npx tsc -b` 通过；对照 §3 不变量逐条给出证据；提交干净聚焦，无调试残留、临时文件、本地配置。

- **Phase 0 保存现状。** 把当前工作区改动按主题拆成聚焦的提交；归档噪声文档。
- **Phase 1 声明与投影地基。** D1、D3、D9、D10；I1–I5、I11 的契约侧；准入门；调用方校验与路由；嵌套调用与 direct 统一到同一管线层；SDK 生成器修正（只为声明了超时的工具生成 `timeout_ms`、区分 integer、拒绝未解析的 `$ref`、名字安全）。保留临时总闸。不改 runtime。
- **Phase 2a 新 runtime（可与 Phase 1 并行，独立 worktree）。** D5、D6；I6、I7、I10 的 runtime 侧；只新增工具无感的 runtime 模块与其测试，不碰工具代码。必须报告：Windows 构建结论、二进制体积增量、冷启动耗时。
- **Phase 2b 接入与切换。** `run_code` 改用新 runtime；D7、D8；I7、I10 端到端；移除 Node 方案与临时总闸；恢复系统提示的工具指导并补 code 模式指导。此阶段结束时 `read/glob/grep` 在产品路径上只能经 `run_code` 调用。
- **Phase 3 写工具 code 化。** `edit`、`write` 声明 Code；I5 在写路径上的完整对等（列举 direct 写的全部执行后副作用并逐项证明嵌套调用同样触发）；审批语义测试；部分完成语义在账本中可见；请求前缀稳定性测试覆盖 code 模式。
- **Phase 4 产品闭环。** 后端在工具目录/设置接口中暴露每个工具的调用面；前端工具卡片显示「code mode」标识（只用主题 token）；`run_code` 不出现在工具开关中；消息列表以 raw 方式正常显示 `run_code`；旧会话回放兼容；交付一份给产品负责人的手工验收清单。
